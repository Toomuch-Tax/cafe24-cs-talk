# 운영 가이드

작은 팀이 운영하는 것을 기준으로 합니다. 가장 큰 위험은 **아무도 모르게 멈춘 것**(연동 만료, 알림 누락, 예약 작업 정지, 답변 지연)이라
상태 화면·슬랙 알림·외부 가동 감시를 먼저 갖춥니다.

## 구성

| 영역 | 기본 | 비고 |
|---|---|---|
| 앱·API | Vercel | 배포마다 버전 보관 → 즉시 롤백 |
| DB | Postgres (Supabase) | 정식 운영 전 유료 전환 권장 (일별 백업·일시정지 없음) |
| 예약 작업 | Vercel Cron 10분 (`/api/cron/jobs`, `vercel.ts`) | 아래 표 |
| 알림 | 슬랙 Incoming Webhook (`SLACK_WEBHOOK_URL`) | 비우면 조용히 건너뜀 |
| 가동 감시 | 외부 모니터(예: UptimeRobot 무료) → `/api/health` | 200 정상, 503 이면 DB 연결 실패 또는 예약 작업 멈춤 |
| 상태 화면 | 콘솔 설정 → **운영 상태** | DB·예약 작업·Cafe24·슬랙·메일·대기열 |

## 예약 작업 (10분마다)

| 작업 | 내용 |
|---|---|
| 답변 지연 경고 | 답변을 기다린 지 `sla_alert_hours`(기본 4시간) 넘은 문의를 모아 슬랙 1회. 영업시간에만 |
| 일일 요약 | 영업일 첫 실행에 하루 1회: 답변 필요 건수, 가장 오래 기다린 시간, 어제 접수/답변, 이번 달 AI 비용 |
| Cafe24 연결 유지 | Refresh Token(14일)이 7일 안에 만료되면 미리 갱신. 실패하면 슬랙으로 재연결 요청 |
| 알림·메일 재시도 | 실패한 작업은 2·4·8·16분 간격으로 최대 5번 |
| 자동 종료 | 답변 후 7일간 고객 추가 문의가 없으면 종료 |
| 개선 후보 | 최근 7일의 반복 오류·AI 미답변 유형·주문 조회 실패를 빈도순으로 모음 (설정 → 운영 개선) |
| 정리 | 오래된 rate limit·OAuth state·작업 기록·행동 기록 삭제. **상담 기록은 지우지 않음** |

- [ ] 첫 백업 + 복원 테스트 (아래)

## 백업과 복원

```bash
npm run backup -- .env.production.local   # ~/CS_Talk_Backups/cs-talk-<날짜>.dump, 최근 30개
npm run restore-test                       # 최신 덤프를 로컬 임시 DB 에 복원해 행 수 확인 후 삭제
```

- 덤프에는 고객 개인정보가 있습니다. 본인만 읽을 수 있게 저장되며, 클라우드 동기화 폴더에 두지 마세요.
- 큰 변경·마이그레이션 직전에는 꼭 수동 백업.
- 실제 복원은 새 DB 에 `pg_restore` 한 뒤 환경변수를 바꿔 재배포합니다. 기존 DB 에 덮어쓰지 않습니다.

## 장애 대응

| 증상 | 볼 곳 | 조치 |
|---|---|---|
| `/api/health` 503 `db:false` | Supabase 상태, 연결 문자열 | 비밀번호 변경·일시정지 여부 확인 |
| `/api/health` 503 `cron:false` | Vercel → Settings → Cron Jobs | 예약 작업 꺼짐·`CRON_SECRET` 확인 |
| 주문 조회 실패 | 설정 → Cafe24 연동 | "다시 연결" |
| 위젯이 안 보임 | 브라우저 콘솔, `WIDGET_ALLOWED_ORIGINS` | 쇼핑몰 주소가 허용 목록에 있는지 |
| AI 가 답을 안 함 | 콘솔 AI 응답 정책 → 설정·응답 기록 | 키·월 예산·주제의 자동 응답 여부 |

## 사람·권한

- 관리자(admin): 설정·사용자·정책 변경. 상담원(agent): 문의 답변.
- 구글 로그인은 `GOOGLE_ALLOWED_DOMAINS` 의 회사 도메인만. 처음 들어온 사람은 설정에 따라 바로 상담원이 되거나 관리자 승인을 기다립니다.
- 퇴사자는 설정 → 사용자에서 비활성화합니다. 설정·사용자·위젯·정책 변경은 설정 → 변경 이력에 남습니다.
